# Formal verification of core specifications (Lean 4)

Status: accepted design, first delivery (eight modules). Branch
`feat/lean-spec`. No issue number; the request is the workflow input of
execution `opus-terra-design-and-implement-review-loop-session-942`.

This document is the source of truth for the formal work. It fixes the
scope, the trust assumptions, the module list, the exact Lean statement of
every theorem, the vector format, the audit and the plan partition. An
implementer may add lemmas and helper definitions, but must not change a
statement in section 6. If a statement is false, the plan reports a concrete
counterexample (a Lean `example` or `#eval` plus the matching TypeScript
input) and the design is updated by review: either the product code is wrong
(fix plus regression test) or the specification text is wrong (correct it
here and state the true theorem).

## 1. Goals and non-goals

Goals:

- A Lean 4.36.0 project in `formal/` that models eight core algorithms,
  states their specified invariants as theorems and proves them with no gaps.
- Each model is a total, executable Lean function that mirrors the structure
  of the TypeScript function it models. A Lean executable emits test vectors
  from the model, and a bun test runs the real TypeScript against them, so a
  model that drifts from the code fails the ordinary test run.
- Every counterexample a proof attempt finds is fixed in code or in design
  text and listed in `docs/formal.md`.

Non-goals:

- No Mathlib, Batteries or other Lake dependency. Core Lean and its standard
  library only.
- No proof about floating point. Where TypeScript uses numbers and the model
  uses integers, the bridging assumption is stated (section 3) and vectors
  stay inside it.
- No Rust models in this delivery.
- `mise run prove` is not part of `mise run verify` and not added to CI
  (`.github/workflows/linux.yml` does not run `mise run verify`).
- The schematic-mode specifications are future modules (section 11).

All eight `lean_exe` entries are written by the scaffold plan up front, so
module plans never edit `lakefile.toml`. So that no gate depends on how Lake
treats an exe whose root is missing, every root always exists: two stub
plans (section 10) create the eight `Nodetto/<Module>/Vectors.lean` files as
stubs (`def main : IO Unit := pure ()`, nothing else), four per plan. Each
module's model plan depends on the stub plan that owns its stub and replaces
it. A stub cannot pass the full audit, because the vector freshness and count
checks fail on empty output. `formal/Nodetto.lean` (the umbrella) is written
by the final docs plan, so no module plan edits a file shared with another
module.

Rules:

- `formal/.lake/` is git-ignored. Plans run Lean only as
  `cd formal && mise exec -- lake build <target>` or
  `mise exec -- lake exe vectors-<file>`, never `lake clean`, and retry a
  build that fails on the build lock.
- Model files import nothing but other model files. `Vectors.lean` files
  import `Nodetto.Json` and their module's Model; they do not import `Lean`.
- Each model definition that mirrors TypeScript has a doc comment naming the
  source path and function, for example
  `/-- Mirrors packages/core/src/fractional.ts keyBetween. -/`.
- The words checked by the audit (section 8) must not appear anywhere in
  `formal/**/*.lean`, comments included.

## 3. Trust assumptions and bridging

Trusted: the Lean 4.36.0 kernel and the axioms `propext`,
`Classical.choice` and `Quot.sound`. Vectors are produced by compiled Lean
code and checked by Bun; they are evidence that the model mirrors the code,
not proofs.

| Id | Bridging assumption (stated, not proved; vectors stay inside it) |
| --- | --- |
| B1 | A JavaScript string is a list of UTF-16 code units. Fractional keys, the NMESH armour text and TSV text are modelled as `List Nat` of code units, so `<` on `List Nat` (core `List.lt`) is JavaScript string `<`. Every other modelled JavaScript string (z-order `ElemId`, Undo ids, and Merge object keys, string values and record ids) is a Lean `String` holding the encoding `E(s)`: four lowercase hex digits per UTF-16 code unit of `s`, in order (`"a"` is `"0061"`, a lone `"\ud800"` is `"d800"`). `E` is injective and total on JavaScript strings, lone surrogates included, which Lean `Char` cannot hold. Because it is fixed-width and `0-9` sort below `a-f`, it also keeps code-unit lexicographic order, so equality, the Undo sorted-id order and member lookup in the model are exactly those of the code. The statements need no hypothesis about `E`: they hold for every `String`. |
| B2 | An `Rng` is a list of draws `u : Nat`; the model takes `0` from an empty list and picks the digit offset `min (u * span / 2^20) (span - 1)`. Coverage: for every number the TypeScript `rng()` can return, including `NaN` and the infinities, the fixed `randomDigitBetween` (D6) picks an offset `o` in `[0, span - 1]`, and the draw `u = ceil(o * 2^20 / span)` (below 2^20) makes the model pick the same `o`. Each call depends on its draw only through `o`, so a theorem quantified over every draw list covers every TypeScript rng sequence. Vectors: the test's rng returns `u / 2^20` for the next draw and `0` once the list is exhausted; for `u < 2^20` and `span <= 62`, `Math.floor(rng() * span)` equals `u * span / 2^20` exactly. Non-finite values are not encoded in vectors; `NaN` is covered by the D6 regression test. |
| B3 | Rotation (Rotate): page coordinates are doubled into integers. `visual.x` and `visual.y` are multiples of 0.5 with magnitude at most 10^6, rotation is one of 0, 90, 180, 270, and catalogue quantities (local box, pin offsets) are multiples of 0.5 pitch. On that domain `rotatePoint` followed by `roundNoise` equals exact integer rotation, and `Math.round(v / 10) * 10` equals `floor((v + 5) / 10) * 10`. |
| B4 | NMESH: bytes are `List Nat`; theorems about arbitrary input require every byte below 256. Coordinates are integers within +-10^7, so every JavaScript integer operation of the codec is exact. |
| B5 | Merge: JSON numbers are modelled as `Int` (integers below 2^53 in magnitude); documents hold no non-integer numbers in vectors. Arrays never hold `undefined`. A model object is the list of a TypeScript object's own enumerable members (`Object.keys`); every key is an ordinary key, `__proto__`, `constructor` and `toString` included, and keys and string values are `E`-encoded (B1), so distinct keys such as `"\ud800"` and `"\ud801"`, which the document parser keeps apart, stay distinct. On this domain `canonicalJson(a) === canonicalJson(b)` (D2) holds exactly when the model's `canon a = canon b`, and the fixed merge reads and writes own members only, so the model's member lookup is the code's. |
| B6 | Overlap: box bounds are integers (sketch grid values in nanometres, at most `Number.MAX_SAFE_INTEGER / 2`), so every comparison is exact. |
| B7 | Sorting: `Array.prototype.sort` with a comparator that is a strict total order returns the unique sorted order, which the model computes with its own sort and the same comparator. |
| B8 | Undo store model: an element is reduced to its id and one integer value (`visual.x`). Only the failures that depend on presence are modelled (create of an existing id, update of a missing id); element validation, references, cascades and pages are outside the model and the conformance test uses elements for which they are inert. |

## 6. Models and theorem statements

Notation: statements are written as they appear inside
`namespace Nodetto.<Module>`. Each fenced block whose info string is
`lean Nodetto.<Module>` holds required theorems; `lean Nodetto.<Module> open`
holds statements that are fixed but may stay open in this delivery (only the
two the intake allows: the NMESH whole-payload round trip and the
segment-tree branch of the overlap search). The audit reads these blocks.
Every statement starts with `theorem <name>`, puts every hypothesis in a
bracketed binder before the final ` :`, and has no proof.

Signatures listed under "Model" are binding (names, argument order and
types). Definitions given in full are binding as written.

### 6.1 Fractional keys (`packages/core/src/fractional.ts`)

Model:

```text
abbrev Key := List Nat                      -- UTF-16 code units (B1)
abbrev Rng := List Nat                      -- draws (B2)
def DIGITS : List Nat                       -- code units of "0-9A-Za-z", in that order
def isFractionalKey (value : Key) : Bool
def randomDigitBetween (low high : Nat) (rng : Rng) : Nat × Rng
def midpoint (lower : Key) (upper : Option Key) (rng : Rng) : Except String (Key × Rng)
def keyBetween (before after : Option Key) (rng : Rng) : Except String (Key × Rng)
def keyAfter (last : Option Key) (rng : Rng) : Except String (Key × Rng)
```

`midpoint` mirrors the TypeScript recursion (shared prefix, room at the
first digit, truncation of `upper`, descent with `upper = none`) and
terminates on the summed lengths of its key arguments. After the D7 fix the
TypeScript runs the descent with `upper = null` as a loop; each iteration is
one recursive `midpoint lower none` call of the model, with the same output
and the same draw. Its digit lookup may
differ from `indexOf` only on code units outside `DIGITS`, which cannot
reach it (both callers validate first).

```lean Nodetto.Fractional
theorem keyBetween_between (lo hi : Key) (rng : Rng)
    (hlo : isFractionalKey lo = true) (hhi : isFractionalKey hi = true) (hlt : lo < hi) :
    ∃ k rng', keyBetween (some lo) (some hi) rng = .ok (k, rng') ∧
      lo < k ∧ k < hi ∧ isFractionalKey k = true

theorem keyBetween_below (hi : Key) (rng : Rng) (hhi : isFractionalKey hi = true) :
    ∃ k rng', keyBetween none (some hi) rng = .ok (k, rng') ∧
      k < hi ∧ isFractionalKey k = true

theorem keyBetween_above (lo : Key) (rng : Rng) (hlo : isFractionalKey lo = true) :
    ∃ k rng', keyBetween (some lo) none rng = .ok (k, rng') ∧
      lo < k ∧ isFractionalKey k = true

theorem keyBetween_unbounded (rng : Rng) :
    ∃ k rng', keyBetween none none rng = .ok (k, rng') ∧ isFractionalKey k = true

theorem keyBetween_rejects_lower (lo : Key) (hi : Option Key) (rng : Rng)
    (h : isFractionalKey lo = false) :
    ∃ e, keyBetween (some lo) hi rng = .error e

theorem keyBetween_rejects_upper (lo : Option Key) (hi : Key) (rng : Rng)
    (h : isFractionalKey hi = false) :
    ∃ e, keyBetween lo (some hi) rng = .error e

theorem keyBetween_rejects_inverted (lo hi : Key) (rng : Rng)
    (hlo : isFractionalKey lo = true) (hhi : isFractionalKey hi = true) (h : ¬ lo < hi) :
    ∃ e, keyBetween (some lo) (some hi) rng = .error e

theorem keyAfter_gt (s : Key) (rng : Rng) :
    ∃ k rng', keyAfter (some s) rng = .ok (k, rng') ∧ s < k

theorem keyAfter_valid (s : Key) (rng : Rng) (h : isFractionalKey s = true) :
    ∃ k rng', keyAfter (some s) rng = .ok (k, rng') ∧ isFractionalKey k = true

theorem keyAfter_none_valid (rng : Rng) :
    ∃ k rng', keyAfter none rng = .ok (k, rng') ∧ isFractionalKey k = true
```

`keyAfter_gt` has no validity hypothesis: the code appends a digit to a
foreign key, which is greater under plain string comparison.

### 6.2 Z-order (`design-z-order.md` section 3, `packages/core/src/z-order.ts`)

Model (imports `Nodetto.Fractional` for `Key`, `Rng`, `keyBetween`,
`keyAfter`, `isFractionalKey`):

```text
abbrev ElemId := String          -- E-encoded id (B1); not `Id`, which is the core identity monad
inductive Action | front | forward | backward | back
inductive Side | before | after
structure Reorder where (id : ElemId) (index : Key)
def relativeOrder (ordered : List ElemId) (moved anchorBlock : ElemId → Bool) (side : Side) : List ElemId
def targetOrder (ordered : List ElemId) (selected : ElemId → Bool) (action : Action) : List ElemId
def targetIds (elements : List (ElemId × Key)) (order : List ElemId) : List ElemId :=
  order.filter (fun id => elements.any (fun e => e.1 == id))
def reorderCommands (elements : List (ElemId × Key)) (order : List ElemId) (rng : Rng) :
    Except String (List Reorder × Rng)
def applyReorders (elements : List (ElemId × Key)) (cmds : List Reorder) : List (ElemId × Key)
def keyOf (elements : List (ElemId × Key)) (id : ElemId) : Key :=
  ((elements.find? (fun e => e.1 == id)).map Prod.snd).getD []
```

`elements` is the page's element list bottom to top (id, index key).
`applyReorders` applies each command in order by replacing the key of the
element with that id, like the store's `reorder` command. The forward and
backward passes mirror the index loops with adjacent swaps. `reorderCommands`
mirrors the fixed code (D3): it returns `[]` when `targetIds` has a length
other than `elements.length` or a duplicate, then the `sameOrder` exit, the
usable-key check with the `renumber` fallback, the `highestKept` pass and the
`keyBetween` pass with its `renumber` fallback.

```lean Nodetto.ZOrder
theorem targetOrder_perm (ordered : List ElemId) (selected : ElemId → Bool) (action : Action) :
    (targetOrder ordered selected action).Perm ordered

theorem targetOrder_selected_order (ordered : List ElemId) (selected : ElemId → Bool) (action : Action) :
    (targetOrder ordered selected action).filter selected = ordered.filter selected

theorem targetOrder_unselected_order (ordered : List ElemId) (selected : ElemId → Bool) (action : Action) :
    (targetOrder ordered selected action).filter (fun id => !selected id) =
      ordered.filter (fun id => !selected id)

theorem targetOrder_front_idem (ordered : List ElemId) (selected : ElemId → Bool) :
    targetOrder (targetOrder ordered selected .front) selected .front =
      targetOrder ordered selected .front

theorem targetOrder_back_idem (ordered : List ElemId) (selected : ElemId → Bool) :
    targetOrder (targetOrder ordered selected .back) selected .back =
      targetOrder ordered selected .back

theorem targetOrder_all_selected (ordered : List ElemId) (selected : ElemId → Bool) (action : Action)
    (h : ∀ id ∈ ordered, selected id = true) :
    targetOrder ordered selected action = ordered

theorem relativeOrder_perm (ordered : List ElemId) (moved anchorBlock : ElemId → Bool) (side : Side) :
    (relativeOrder ordered moved anchorBlock side).Perm ordered

theorem relativeOrder_moved_order (ordered : List ElemId) (moved anchorBlock : ElemId → Bool) (side : Side) :
    (relativeOrder ordered moved anchorBlock side).filter moved = ordered.filter moved

theorem relativeOrder_unmoved_order (ordered : List ElemId) (moved anchorBlock : ElemId → Bool) (side : Side) :
    (relativeOrder ordered moved anchorBlock side).filter (fun id => !moved id) =
      ordered.filter (fun id => !moved id)

    (h : ∀ id ∈ ordered, moved id = false → anchorBlock id = false) :
    relativeOrder ordered moved anchorBlock side = ordered

theorem relativeOrder_before (ordered : List ElemId) (moved anchorBlock : ElemId → Bool)
    (h : ∃ id ∈ ordered, moved id = false ∧ anchorBlock id = true) :
    ∃ pre post, relativeOrder ordered moved anchorBlock .before = pre ++ ordered.filter moved ++ post ∧
      pre ++ post = ordered.filter (fun id => !moved id) ∧
      (∀ id ∈ pre, anchorBlock id = false) ∧
      ∃ a rest, post = a :: rest ∧ anchorBlock a = true

theorem relativeOrder_after (ordered : List ElemId) (moved anchorBlock : ElemId → Bool)
    (h : ∃ id ∈ ordered, moved id = false ∧ anchorBlock id = true) :
    ∃ pre post, relativeOrder ordered moved anchorBlock .after = pre ++ ordered.filter moved ++ post ∧
      pre ++ post = ordered.filter (fun id => !moved id) ∧
      (∀ id ∈ post, anchorBlock id = false) ∧
      ∃ init a, pre = init ++ [a] ∧ anchorBlock a = true

theorem reorderCommands_refuses (elements : List (ElemId × Key)) (order : List ElemId) (rng : Rng)
    (h : ¬ (targetIds elements order).Perm (elements.map Prod.fst)) :
    reorderCommands elements order rng = .ok ([], rng)

theorem reorderCommands_unchanged (elements : List (ElemId × Key)) (order : List ElemId) (rng : Rng)
    (h : targetIds elements order = elements.map Prod.fst) :
    reorderCommands elements order rng = .ok ([], rng)

theorem reorderCommands_spec (elements : List (ElemId × Key)) (order : List ElemId) (rng : Rng)
    (hnd : (elements.map Prod.fst).Nodup)
    (hperm : (targetIds elements order).Perm (elements.map Prod.fst))
    (hmove : targetIds elements order ≠ elements.map Prod.fst) :
    ∃ cmds rng', reorderCommands elements order rng = .ok (cmds, rng') ∧
      ((targetIds elements order).map (keyOf (applyReorders elements cmds))).Pairwise (· < ·) ∧
      ∀ e ∈ elements, (∀ c ∈ cmds, c.id ≠ e.1) → keyOf (applyReorders elements cmds) e.1 = e.2
```

`relativeOrder_before` and `relativeOrder_after` are the section 3 rule
"`before` lands below the lowest element of the anchor block and `after`
above the highest", with the moved block kept contiguous and in order.
`reorderCommands_spec` says the final keys strictly increase along the
target order (so they are distinct and sort into it) and that an element
without a command keeps its key. `hnd` is the store invariant (ids are
unique on a page).

#### 6.2.1 Proof architecture for `reorderCommands` (fv-24)

This subsection fixes how the three `reorderCommands_*` statements above are
proved. It does not change them. The statements of `reorderCommands_refuses`
and `reorderCommands_unchanged` in `formal/Nodetto/ZOrder/Reorder.lean` are
already character-for-character the ones above, and the audit accepts both
with only the allowed axioms. Only `reorderCommands_spec` is missing. Every
lemma below is a `private` helper in `formal/Nodetto/ZOrder/Reorder.lean`
and is not audited by name. An implementer may strengthen a helper, split
it, or fix a helper statement that turns out false, provided the three
section 6.2 statements stay verbatim. Any such change is recorded in the
plan's progress file.

Status of the existing helpers (all build, none needs changing). These are
reused by name: `target_guard_false` (guard is false under the spec
hypotheses), `targetIds_subset`, `keyOf_valid_of_member`, `between_bounds`
(the four `keyBetween_*` theorems for optional valid ordered bounds),
`sorted_keys_append`, `scan_moved_mem`, `scan_moved_preserved`,
`keyOf_apply_member`, `keyOf_apply_other`, `untouched_element`,
`renumber_applied_sorted` (renumber gives sorted applied keys for every rng)
and `reorderCommands_renumber_spec` (the full spec conclusion when the
original keys are invalid or duplicated). So two parts are left: the
valid-key branch (scan, loop and composition) and the final case split.

Proof outline of `reorderCommands_spec`:

1. The second conjunct (untouched elements keep their key) holds for every
   command list by `untouched_element`, so only "returns `.ok`" and the
   ordering conjunct need the algorithm.
2. Case split on the key check `(!(elements.map Prod.snd).all isFractionalKey
   || (elements.map Prod.snd).eraseDups.length != (elements.map Prod.snd).length)`.
   If it is `true`, use `reorderCommands_renumber_spec`. If it is `false`,
   every key is valid (distinctness is not needed). The function then
   reduces to `loop target [] [] rng`, where `moved` is the result of the
   `highestKept` scan.
3. Scan: along `target`, the keys of the kept ids (those with
   `moved.contains id = false`) strictly increase.
4. Loop invariant `LoopInv`. The keys in `done` strictly increase and are
   valid. Each is below the original key of every kept id still in `rest`.
   `cmds` is exactly the moved part of `done`, and the kept entries of
   `done` carry their original keys. A kept step appends its original key.
   A moved step appends the `keyBetween below above` result, and
   `between_bounds` places that key above `below` (the last `done` key) and
   below `above` (the first kept key in `rest`). Validity of both bounds
   comes from the invariant. The in-loop renumber fallback cannot fire, but
   the proof does not show that: it handles the branch through
   `renumber_applied_sorted`.
5. At the end, `done.map Prod.fst = target`. Applying `cmdsOf moved done`
   gives every kept id its original key and every moved id its new key, so
   the applied keys along `target` are `done.map Prod.snd`, which is sorted.

Loop signature. `let rec loop` compiles to the auxiliary
`reorderCommands.loop`, whose leading arguments are the captured variables.
The expected form, used below, is
`reorderCommands.loop elements target moved rest done cmds state` with
`target := targetIds elements order`. The first plan of the chain checks it
with a temporary `#check @reorderCommands.loop` (removed before the plan
finishes). If Lean captured a different list or order (for example `order`
with `targetIds elements order` inlined), the helpers take that argument
list instead and the rest is unchanged. This adapts private helpers only and
weakens nothing.

Lemma statements (inside `namespace Nodetto.ZOrder` with
`open Nodetto.Fractional`). They are grouped in dependency order. Each group
is about one implementer sitting.

```lean Nodetto.Nmesh
theorem unzigzag_zigzag (d : Int) :
    unzigzag (zigzag d) = d
```

### 6.5 Anchored rotation (`design-breadboard.md` 4.2, `packages/core/src/breadboard/rotate.ts`)

Model, in doubled page units (B3). For a part with local box `L` (pitches)
and pin definitions `(dx, dy)` (pitches), `cx = 10 * L.width`,
`cy = 10 * L.height` (twice the half box, in page units) and a pin's
unrotated doubled offset from `visual` is `(20 * (dx - L.x), 20 * (dy - L.y))`.

```text
structure Geometry where
  cx : Int
  cy : Int
  pins : List (Int × Int)          -- catalogue order; head is pin 1
structure Part where
  x : Int                          -- 2 * visual.x
  y : Int                          -- 2 * visual.y
  turns : Fin 4                    -- visual.rotation / 90
inductive Turn | cw | ccw          -- quarterTurns 1 and -1 (clockwise on the y-down page)
def rotateVec (t : Fin 4) (v : Int × Int) : Int × Int   -- t quarter turns of (dx, dy) ↦ (-dy, dx)
def pinPositions (g : Geometry) (p : Part) : List (Int × Int)
  -- each pin q ↦ (p.x, p.y) + (g.cx, g.cy) + rotateVec p.turns (q - (g.cx, g.cy))
def rotate (g : Geometry) (p : Part) (t : Turn) : Option Part
  -- mirrors one loop iteration of planBreadboardRotation; none when g.pins = []
```

Binding definitions:

```text
def anchor (g : Geometry) (p : Part) : Option (Int × Int) := (pinPositions g p).head?

  ∀ q0 ∈ g.pins.head?, ∀ q ∈ g.pins, (20 : Int) ∣ q.1 - q0.1 ∧ (20 : Int) ∣ q.2 - q0.2
```

### 6.6 Undo/redo history (`packages/core/src/history.ts`, `commands.ts`)

History model (stacks are lists with the top at the head):

```text
structure Entry (C : Type) where
  undo : List C
  redo : List C
structure History (C : Type) where
  undoStack : List (Entry C)
  redoStack : List (Entry C)
  depth : Nat                      -- batchDepth
  pending : Option (Entry C)
  limit : Nat
def History.push {C : Type} (h : History C) (e : Entry C) : History C
def History.beginBatch {C : Type} (h : History C) : History C
def History.endBatch {C : Type} (h : History C) : History C
def History.abortBatch {C : Type} (h : History C) : History C × Option (List C)  -- commands run
def History.undo {C : Type} (h : History C) : Option (List C × History C)        -- commands run
def History.redo {C : Type} (h : History C) : Option (List C × History C)
def History.clear {C : Type} (h : History C) : History C
def nonEmpty {C : Type} (es : List (Entry C)) : List (Entry C) := es.filter (fun e => !e.undo.isEmpty)
def Inverts {C D : Type} (run : List C → D → D) (e : Entry C) : Prop := ∀ d, run e.undo (run e.redo d) = d
```

Listeners and `emit` are not modelled. Store model (B8):

```text
abbrev ElemId := String          -- E-encoded id (B1); not `Id`, which is the core identity monad
abbrev Store := List (ElemId × Int)
inductive Cmd | create (id : ElemId) (value : Int) | delete (ids : List ElemId) | update (id : ElemId) (value : Int)
def lookup (s : Store) (id : ElemId) : Option Int
def applyCommands (s : Store) (cs : List Cmd) : Except String (Store × List Cmd)
```

`create` mirrors `createElement` (fails when the id exists; inverse
`delete [id]`), `delete` mirrors `deleteElements` without references
(missing ids skipped; inverse `create` per removed id in sorted id order),
`update` mirrors `replaceVisual` (fails when the id is missing; inverse
`update` with the previous value). The inverse list is built front-first
like `undo.unshift`, and any failure fails the whole list.

```lean Nodetto.Undo
theorem undo_then_redo {C : Type} (h : History C) (e : Entry C) (rest : List (Entry C))
    (hu : h.undoStack = e :: rest) :
    ∃ h1, h.undo = some (e.undo, h1) ∧ h1.redo = some (e.redo, h)

theorem redo_then_undo {C : Type} (h : History C) (e : Entry C) (rest : List (Entry C))
    (hr : h.redoStack = e :: rest) :
    ∃ h1, h.redo = some (e.redo, h1) ∧ h1.undo = some (e.undo, h)

theorem push_clears_redo {C : Type} (h : History C) (e : Entry C)
    (hne : e.undo ≠ []) (hd : h.depth = 0) :
    h.push e = { h with undoStack := (e :: h.undoStack).take h.limit, redoStack := [] }

theorem push_empty {C : Type} (h : History C) (e : Entry C) (he : e.undo = []) :
    h.push e = h

theorem abortBatch_keeps_stacks {C : Type} (h : History C) :
    h.abortBatch.1.undoStack = h.undoStack ∧ h.abortBatch.1.redoStack = h.redoStack

theorem batch_one_step {C : Type} (h : History C) (es : List (Entry C))
    (hd : h.depth = 0) (hp : h.pending = none) (hne : nonEmpty es ≠ []) :
    (es.foldl History.push h.beginBatch).endBatch =
      { h with
        undoStack := (Entry.mk ((nonEmpty es).reverse.flatMap Entry.undo)
          ((nonEmpty es).flatMap Entry.redo) :: h.undoStack).take h.limit,
        redoStack := [] }

theorem batch_noop {C : Type} (h : History C) (es : List (Entry C))
    (hd : h.depth = 0) (hp : h.pending = none) (hall : nonEmpty es = []) :
    (es.foldl History.push h.beginBatch).endBatch = h

theorem abortBatch_reverts {C : Type} (h : History C) (es : List (Entry C))
    (hd : h.depth = 0) (hp : h.pending = none) (hne : nonEmpty es ≠ []) :
    (es.foldl History.push h.beginBatch).abortBatch =
      (h, some ((nonEmpty es).reverse.flatMap Entry.undo))

theorem batch_inverts {C D : Type} (run : List C → D → D)
    (hnil : ∀ d, run [] d = d) (hrun : ∀ xs ys d, run (xs ++ ys) d = run ys (run xs d))
    (es : List (Entry C)) (h : ∀ e ∈ es, Inverts run e) :
    Inverts run (Entry.mk (es.reverse.flatMap Entry.undo) (es.flatMap Entry.redo))

theorem applyCommands_undo (s s' : Store) (cs u : List Cmd)
    (h : applyCommands s cs = .ok (s', u)) :
    ∃ t u', applyCommands s' u = .ok (t, u') ∧ ∀ id, lookup t id = lookup s id
```

`batch_one_step` with `undo_then_redo` is "a batch undoes as one step in
reverse order"; `batch_inverts` shows that the reversed concatenation undoes
the batch when each recorded entry undoes its own edit.

### 6.7 Three-way merge (`design-cli-layout-merge-lint.md` B1, `packages/core/src/document-merge.ts`)

Model (B5). `ours` and `theirs` stand for the code's `local` and `remote`
(`local` is a Lean keyword). Every `String` below (object keys, `J.str`
values, record ids) is the `E` encoding of the JavaScript string (B1).

```text
inductive J
  | null | bool (b : Bool) | num (n : Int) | str (s : String)
  | arr (items : List J) | obj (fields : List (String × J))
def canon : J → J                              -- objects: first occurrence per key, keys sorted, recursively
def same (a b : Option J) : Bool               -- none is undefined; canon equality (D2)
def mergeValue (base ours theirs : Option J) : Option J × Bool   -- value, conflict flag
def getPath (v : Option J) (path : List String) : Option J
def diffPaths (base v : Option J) : List (List String)
inductive Reason | bothChanged | deletedLocally | deletedRemotely
structure Conflict where (id : String) (reason : Reason)
def mergeById (base ours theirs : List (String × J)) : List (String × J) × List Conflict
def find (records : List (String × J)) (id : String) : Option J   -- last match, like Map
```

Proof boundary: the models and theorems cover only the live editor's
helpers `mergeValue` and `mergeById` in `document-merge.ts`, which
`mergeDocuments` uses. The CLI's `mergeDocumentVersions` has its own
recursive `value` and `records` routines with a different conflict policy:
it carries the `added` flag through nested objects, merging every
both-added nested object against `{}`, and reports field paths and
`both-added`. The two routines share only `same` (D2) and the own-member
rules. Example: both sides add page `q`, ours with `extensions` `{ours: 1}`
and theirs with `extensions` `{theirs: 2}`. `mergeDocuments` (live) reports
`both-changed` on `q` and keeps ours' `extensions`, because only the record
root merges against `{}` (`recordBase`). `mergeDocumentVersions` (CLI) keeps
both fields with no conflict. No theorem here describes the CLI routines,
and this design does not change either policy.

`mergeValue` mirrors the fixed code: the three `same` checks in order, the
object branch over the first-occurrence union of base, ours and theirs keys
(omitting undefined results), else conflict and ours. Object member lookup
takes the first occurrence, which is the code's own-member read (B5).
`mergeById` mirrors the code over records given as `(id, record)`, with ids
in first-occurrence order of ours, theirs, base.

Binding definitions:

```text
def getPath : Option J → List String → Option J
  | v, [] => v
  | some (.obj fs), k :: p => getPath (lookupFirst fs k) p
  | _, _ :: _ => none
def diffPaths (b v : Option J) : List (List String) :=
  if same b v then []
  else match b, v with
    | some (.obj bs), some (.obj vs) =>
        (keysUnion bs vs).flatMap fun k => (diffPaths (lookupFirst bs k) (lookupFirst vs k)).map (k :: ·)
    | _, _ => [[]]
def FieldConflict (b l r : Option J) : Prop :=
  ∃ p ∈ diffPaths b l, ∃ q ∈ diffPaths b r,
    (p <+: q ∨ q <+: p) ∧ ¬ (p = q ∧ same (getPath l p) (getPath r p) = true)
def recordBase : Option J → Option J → Option J → Option J
  | none, some _, some _ => some (.obj [])
  | b, _, _ => b
```

`keysUnion` is the first-occurrence union of the two key lists;
`lookupFirst` returns the first member with that key. `diffPaths b v` is the
set of maximal paths where `v` changed against `b`, descending only through
objects; `FieldConflict` is "both sides changed the same field (or one
changed a field inside what the other replaced) differently". `recordBase`
is the B1 rule that a record added on both sides merges against an empty
object.

```lean Nodetto.Merge
theorem mergeValue_unchanged_ours (b t : Option J) :
    same (mergeValue b b t).1 t = true ∧ (mergeValue b b t).2 = false

theorem mergeValue_unchanged_theirs (b o : Option J) :
    same (mergeValue b o b).1 o = true ∧ (mergeValue b o b).2 = false

theorem mergeValue_same_change (b x : Option J) :
    mergeValue b x x = (x, false)

theorem mergeValue_symm (b l r : Option J) (h : (mergeValue b l r).2 = false) :
    (mergeValue b r l).2 = false ∧ same (mergeValue b l r).1 (mergeValue b r l).1 = true

theorem mergeValue_conflict_iff (b l r : Option J) :
    (mergeValue b l r).2 = true ↔ FieldConflict b l r

theorem mergeById_unchanged_ours (B T : List (String × J)) :
    (mergeById B B T).2 = [] ∧ ∀ id, same (find (mergeById B B T).1 id) (find T id) = true

theorem mergeById_unchanged_theirs (B O : List (String × J)) :
    (mergeById B O B).2 = [] ∧ ∀ id, same (find (mergeById B O B).1 id) (find O id) = true

theorem mergeById_same_change (B X : List (String × J)) :
    (mergeById B X X).2 = [] ∧ ∀ id, same (find (mergeById B X X).1 id) (find X id) = true

theorem mergeById_symm (B L R : List (String × J)) (h : (mergeById B L R).2 = []) :
    (mergeById B R L).2 = [] ∧
      ∀ id, same (find (mergeById B L R).1 id) (find (mergeById B R L).1 id) = true

theorem mergeById_conflict_iff (B L R : List (String × J)) (id : String) :
    id ∈ (mergeById B L R).2.map Conflict.id ↔
      FieldConflict (recordBase (find B id) (find L id) (find R id)) (find L id) (find R id)
```

Equality of merged values is `same` (semantic JSON equality), because the
result's key order follows the input order and differs when ours and theirs
are swapped. Record order in `mergeById` results is likewise compared per
id.

Decision on key order (D2): comparing `JSON.stringify` output is a
specification defect, because key order is not part of a JSON value's
meaning and the documents are serialized in canonical order anyway. The fix
makes `same` key-order-insensitive, so "changed" in `diffPaths` and
`FieldConflict` means a change of JSON value. With the old comparison the
statements would only hold for a notion of change that counts key order: in
the D2 example ours did not change as a JSON value, so `diffPaths b ours` is
empty and no conflict may be reported, but the old code reports one and
drops theirs' change. The conformance test runs every `mergeValue` vector
with reversed key order to pin this.

### 6.8 Overlap search (`design-cad3d.md` F8, `packages/core/src/cad/loops.ts`)

Model (B6, B7). `stop`, `count` and `crowded` are instrumentation and are
not modelled (no stop; `crowded` absent).

```text
structure Box where
  minX : Int
  minY : Int
  maxX : Int
  maxY : Int
inductive Axis | x | y
inductive Branch | sweepX | sweepY | tree
def overlaps (a b : Box) : Bool :=
  decide (a.minX ≤ b.maxX) && decide (b.minX ≤ a.maxX) && decide (a.minY ≤ b.maxY) && decide (b.minY ≤ a.maxY)
def bruteForce (boxes : List Box) : List (Nat × Nat) :=
  (List.range boxes.length).flatMap fun i =>
    ((List.range boxes.length).filter fun j =>
      decide (i < j) && (match boxes[i]?, boxes[j]? with
        | some a, some b => overlaps a b
        | _, _ => false)).map fun j => (i, j)
def norm (p : Nat × Nat) : Nat × Nat := (min p.1 p.2, max p.1 p.2)
def sweep (boxes : List Box) (axis : Axis) : List (Nat × Nat)       -- visits of the sweep branch on that axis
def treeSearch (boxes : List Box) : List (Nat × Nat)                -- visits of the segment-tree branch
def overlappingPairs (boxes : List Box) : Branch × List (Nat × Nat) -- branch choice via overlapCount
```

```lean Nodetto.Overlap
theorem sweep_visits_overlaps (boxes : List Box) (axis : Axis) :
    ((sweep boxes axis).map norm).Perm (bruteForce boxes)

theorem overlappingPairs_sweep (boxes : List Box) (h : (overlappingPairs boxes).1 ≠ .tree) :
    ((overlappingPairs boxes).2.map norm).Perm (bruteForce boxes)
```

```lean Nodetto.Overlap open
theorem treeSearch_visits_overlaps (boxes : List Box) :
    ((treeSearch boxes).map norm).Perm (bruteForce boxes)

theorem overlappingPairs_visits_overlaps (boxes : List Box) :
    ((overlappingPairs boxes).2.map norm).Perm (bruteForce boxes)
```

`Perm` against `bruteForce` means every overlapping unordered pair (closed
boxes, touching counts) is visited exactly once and nothing else is. The
statements carry no well-formedness hypothesis (min at most max): the sweep
only skips pairs whose sweep-axis intervals are disjoint. If the open pair is
not finished, the tree branch is covered by vectors and listed as open.

## 7. Vectors

Each `lake exe vectors-<file>` prints one JSON document to stdout,
deterministically (fixed enumerations plus a fixed-seed linear
congruential generator in Lean; no clock, no IO randomness):

```text
{"module":"<file>","sources":["<ts path>",...],"generator":"formal/Nodetto/<Module>/Vectors.lean","cases":[
{"fn":"<function>","in":{...},"out":{...}},
...
]}
```

- One case per line, keys in the order shown, a trailing newline, ASCII
  only. Integers are JSON numbers within 2^53.
- Strings: every modelled string (a `List Nat` of code units, or an
  `E`-encoded `String`, B1) is written as a JSON string. `Nodetto/Json.lean`
  takes its UTF-16 code units and writes printable ASCII other than `"` and
  `\` as itself, and every other code unit as `\uXXXX` (lowercase hex). So
  `JSON.parse` in the test yields exactly the JavaScript string the model
  stands for, lone surrogates included, and expected and actual values are
  compared as plain JavaScript strings, with no extra decoding in the test.
  The generator decodes `E` and fails on a malformed `E` string.
- `merge.json` must contain at least these surrogate cases: (a) one object
  with own keys `"\ud800"` and `"\ud801"`, where ours changes the
  `"\ud800"` member and theirs changes the `"\ud801"` member: the merge
  keeps both changes and reports no conflict; (b) ours sets the `"\ud800"`
  member and theirs sets the `"\ud801"` member of an object where both were
  absent in base: both kept, no conflict; (c) a string value whose base is
  `"\ud800"`, with ours `"\ud801"` and theirs unchanged: the result is
  ours with no conflict. Mapping both keys to one value (for example
  U+FFFD) changes the outcome of each case, so these cases detect such a
  conflation.
- `out` is `{"ok":<value>}` or `{"error":"<code>"}`. Fractional and
  z-order errors use the code `"range"` (TypeScript throws `RangeError`);
  NMESH uses the `NmeshError` codes (`nmesh.truncated`, ...); the Undo store
  uses `"command"` (TypeScript throws `CommandError`).
- At least 200 cases per module and at least 20 per modelled public
  function (the Rotate `fixture` header cases are exempt from the
  per-function minimum), including boundary cases: empty inputs, single elements, keys
  ending in `z`, keys with shared prefixes, adjacent digits, varints at
  2^7, 2^14, 2^21, 2^28 and 2^32 - 1, overlong and truncated varints, bad
  magic, flags, unit, CRC, counts and trailing bytes, armour padding 0, 1
  and 2, empty rows and fields with tab, quote, CR and LF, all four
  rotations both ways with on- and off-lattice anchors, nested batches and
  aborts, delete of missing ids, key-reordered objects, both-added records,
  touching boxes and grids crowded enough to take the tree branch.
- Per-module `in` and `out`:

| File | Cases |
| --- | --- |
| `fractional.json` | `isFractionalKey` {value} -> bool; `keyBetween` {before, after, draws} -> key or error; `keyAfter` {last, draws} -> key |
| `z-order.json` | `targetOrder` {ordered, selected, action} -> ids; `relativeOrder` {ordered, moved, anchorBlock, side} -> ids; `reorderCommands` {elements: [[id, key]], order, draws} -> [[id, key]] commands |
| `nmesh.json` | `encodeNmesh` {positions, triangles, groups} -> bytes or error; `decodeNmesh` {bytes} -> mesh or error; `toInline` {bytes} -> string or error; `fromInline` {text} -> bytes or error |
| `tsv.json` | `parseTsv` {text} -> grid; `serializeTsv` {grid} -> text; `roundTrip` {grid} -> grid |

| `merge.json` | `mergeValue` {base, ours, theirs} -> {value, conflict}; `mergeById` {base, ours, theirs} -> {records, conflicts: [[id, reason]]} |

The sweep axis is not written, because the TypeScript interface does not expose it; it is checked through `visits`. The generator must include at least 20 axis-discriminating cases, where `sweep boxes .x` and `sweep boxes .y` give different visit sequences and the model takes the sweep branch: at least 5 where X wins strictly, at least 5 where Y wins strictly, and at least 5 ties (`alongX = alongY`, where X is chosen). The generator fails if it cannot produce them. |

Conformance tests (section 4 paths) read
`formal/vectors/<file>.json` relative to `import.meta.url` with
`readFileSync`, validate the shape with a typed guard (no `any`; indexed
reads typed for `noUncheckedIndexedAccess`), and assert the real
implementation returns `out` for every case:

- Fractional, z-order: the rng closure of B2; z-order checks the emitted
  commands exactly. `NaN` is not a vector value; the D6 regression test in
  `fractional.test.ts` covers it.
- NMESH: exact bytes for encode, exact mesh or `NmeshError.code` for
  decode, exact strings for armour.
- Rotate: build each fixture element with the catalogue, assert
  `breadboardLocalBox` and `breadboardPinDefs` give the fixture's geometry
  and that it satisfies `PinsOnPitch`, then run `planBreadboardRotation` on a
  store and compare `{x, y, rotation}` with the model output halved.
- Undo: drive a real `History` with a recording runner and compare what ran
  and `undoSize`/`redoSize`/`batching` after each op; run `applyCommands` on
  a real `Store` with elements whose `visual.x` is the model value and
  compare the resulting values and the undo commands.
- Merge: call the exported `mergeValue` and `mergeById`; compare values with
  `toEqual` (key-order-insensitive) and conflicts exactly; additionally run
  each `mergeValue` case with every object's keys reversed and expect the
  same result (exercises D2). Reversed copies are made by `JSON.parse` of
  the reversed JSON text, so own `__proto__` members survive. Vector inputs include objects with the own
  keys `__proto__`, `constructor` and `toString`. The test builds inputs with
  `JSON.parse`, so these become own members as they do in documents.
- Overlap: call the exported `overlappingPairs` with a recording `visit`, a
  no-op `count`, no `stop`, and a `crowded` callback that records that it
  was called and returns true. For every case, assert that `crowded` was
  called exactly when `tree` is true, and assert the exact ordered visit
  sequence. The test does not re-implement the branch selector. A wrong axis
  choice fails on the axis-discriminating cases, and the crowded cases run
  the real tree branch.

These tests run in the ordinary `bun test` (and so in `mise run test`); they
need only the committed JSON, not Lean.

## 8. Audit and the prove task

`formal/scripts/audit.ts` (Bun, strictly typed; `formal/scripts` is added to
the `tsconfig.json` include list and to `biome.json` `files.include`).
`formal/scripts/audit` is the executable wrapper. Usage:

```text
formal/scripts/audit                                       full mode (the prove task)
formal/scripts/audit --list                                list mode: parse and print the statements; no Lean
formal/scripts/audit --module <M> --vectors                vector mode: one module's vectors
formal/scripts/audit --module <M> --theorem <name>...      theorem mode: the named statements of one module
```

The modes run these steps:

| Mode | Steps | Needs |
| --- | --- | --- |
| list | parse section 6 only; print `<module> <required or open> <name>` per statement and the totals (66 required, 3 open); fail on a malformed block | this document |
| vector | 1 on `formal/Nodetto/<M>.lean` and `formal/Nodetto/<M>/`; 2 for `Nodetto.<M>`; 4 for the module | scaffold, stubs, Json, the module's model |
| theorem | 1 and 2 as in vector mode; 3 for the named statements only (each must exist; open-block names may be given once their proof lands) | the module's model and the proof files that contain the named theorems |
| full | 1 on all of `formal/`; 2 for `Nodetto` (the umbrella); 3 for every statement, including the open-block rule; 4 for all eight modules | every plan, including docs (`docs/formal.md`, umbrella) |

Only full mode reconciles open statements with `docs/formal.md`; vector
and theorem modes never read it. Only vector and full mode run vector
freshness. So a model plan does not need any theorem, and a proof plan does
not need the conformance test or the docs.

Steps, each failing the run with a message:

1. Forbidden tokens: scan the selected `.lean` files (full mode: `formal/**/*.lean` excluding `formal/.lake`) for
   the words `sorry`, `admit`, `axiom`, `native_decide`, `unsafe`,
   `partial`, `opaque`, `implemented_by`, `extern`, `skipKernelTC` and
   `#exit` (word boundaries; comments included), and for any
   `maxHeartbeats` value above 400000 or equal to 0.
2. Build: `mise exec -- lake build Nodetto.<M>` per selected module (all:
   `lake build Nodetto`), from `formal/`.
3. Statements: parse the fenced blocks of this document whose info string
   is `lean Nodetto.<M>` or `lean Nodetto.<M> open`. For each statement
   `theorem N B : C` write into `formal/.lake/audit/Check<M>.lean`:
   `import Nodetto.<M>`, `namespace Nodetto.<M>`,
   `example : ∀ B, C := @N` (or `example : C := @N` without binders),
   `end Nodetto.<M>` and `#print axioms Nodetto.<M>.N`; run it with
   `mise exec -- lake env lean`. Any elaboration error fails (missing
   theorem or a different signature, including an added hypothesis). Every
   printed axiom must be one of `propext`, `Classical.choice`, `Quot.sound`.
   In full mode, a statement from an `open` block whose name does not occur
   as a declaration in the module's sources is skipped only if
   `docs/formal.md` lists it under "Open"; otherwise the run fails. A
   required statement is never skipped. In theorem mode only the named
   statements are checked.
4. Vectors: run `mise exec -- lake exe vectors-<file>` into
   `formal/.lake/audit/<file>.json` and compare byte for byte with
   `formal/vectors/<file>.json`; check at least 200 cases and at least 20
   per function name other than `fixture`.

`mise.toml` gains:

```toml
[tasks.prove]
description = "Build the Lean proofs, audit them and check the committed vectors"
run = "formal/scripts/audit"
```

`prove` is not added to `verify`, `test` or `ci`. The full run must finish
in about ten minutes on a laptop; no declaration may need `maxHeartbeats`
above 400000, and `decide` is used only on small literals (the D1
counterexamples), never over a finite space in place of a proof.

  `{"x":1,"__proto__":1}`, ours `{"x":2,"__proto__":1}`, theirs
  `{"x":1,"__proto__":2}` (built with `JSON.parse`) merge key by key to an
